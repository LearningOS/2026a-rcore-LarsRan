# rCore 第六章实验报告（lab4）：文件系统

## 一、功能总结

本次实验完成了 ch6 文件系统系统调用与底层支持：实现 `linkat`、`unlinkat`
和 `fstat`；为磁盘 inode 增加硬链接计数；实现目录项共享、链接计数更新以及最后
一个链接删除后的 inode、直接块和间接块回收；完善文件状态查询和跨页用户内存复制。
同时修复 easy-fs 块缓存刷盘问题，保证文件镜像中的间接数据完整。ch3 至 ch5 的
功能均保持兼容。

## 二、文件系统设计

### 2.1 分层结构

- `easy-fs` 负责磁盘格式、块缓存、位图分配、inode 与目录项管理。
- 内核 `fs` 层用 `OSInode` 封装 `easy-fs::Inode`，并为文件描述符提供统一接口。
- `File` trait 向上提供读写、同步和状态查询，`syscall/fs.rs` 负责用户指针翻译及
  系统调用参数检查。
- 当前实验只使用根目录，因此路径操作均从根 inode 开始；`dirfd` 和 `flags`
  不参与实际寻址。

### 2.2 硬链接

`link` 先在根目录中确认原文件存在、新旧名称不同且新名称未被占用，然后追加一个
新的目录项。新目录项保存目标 inode 的编号，而不是复制文件数据，因此两个名称
对应同一份数据块，并具有相同的 `dev` 和 `ino`。目录项写入成功后，目标
`DiskInode.nlink` 增加一。文件系统互斥锁覆盖“检查名称、追加目录项、更新计数”
这一组操作，避免并发硬链接产生重复名称或计数错误。

若原文件不存在、名称为空、名称过长、新名称已存在或新旧名称相同，操作返回错误。
目录不会通过本实验的接口建立硬链接。

### 2.3 取消链接与资源回收

`unlink` 根据名称找到目标 inode，并拒绝删除目录。删除普通文件时，目录是连续
排列的目录项数组，因此需要把被删除项之后的目录项依次前移，再缩小目录大小，
避免线性查找在空洞处提前结束。

随后将目标 inode 的 `nlink` 减一：

- 计数仍大于零时，只删除当前名称，其他目录项继续引用同一 inode。
- 计数减到零时，先取得该 inode 持有的直接块、一级间接块、二级间接块及所有
  数据块，再逐个清空并归还数据位图；最后清零磁盘 inode 并释放 inode 位图。

回收顺序保证旧 inode 不会在数据块仍被访问时被重新分配。位图释放前会检查对应位
确实处于已分配状态，以避免重复释放。

### 2.4 文件状态查询

`fstat` 先验证文件描述符并取得对应的 `File` 对象。`OSInode::stat` 返回以下信息：

| 字段 | 含义 |
| --- | --- |
| `dev` | 固定为 0，表示当前只有一块块设备 |
| `ino` | 文件所在 inode 的持久编号 |
| `mode` | `FILE` 或 `DIR` |
| `nlink` | 当前硬链接数量 |
| `pad` | 兼容保留字段，填零 |

`Stat` 位于用户地址空间，目标地址可能跨越两个物理页。实现通过逐页翻译复制，
而不是把用户地址直接当作可连续访问的内核指针，因此跨页访问安全。

### 2.5 块缓存与持久化

块缓存最多保留 16 个磁盘块，修改过的缓存项在淘汰时写回。若系统退出时仍有未
淘汰的脏块，普通生命周期不会自动触发缓存项析构，可能导致文件末尾的数据没有进入
磁盘镜像。为此：

1. 文件系统实例释放时统一刷新全部脏块；
2. 官方打包流程在写完每个 ELF 后显式同步该 inode。

该修复保证超过 28 个直接数据块、需要使用间接块的文件也能被完整写入镜像。

## 四、性能与可靠性分析

- 目录查找为线性扫描，符合 easy-fs 的简单设计；当前文件数量较少，开销可接受。
- 块缓存减少重复块设备读取，目录和 inode 更新先在缓存中完成，由淘汰或统一同步
  写回，避免每次写入都刷新整个缓存。
- `unlink` 只在 `nlink == 0` 时释放数据块和 inode；普通删除一个链接不会误删
  其他名称仍在使用的数据。
- 所有系统调用在访问用户指针前进行翻译和边界检查，避免内核直接解引用恶意地址。
- 解析文件描述符时只复制 `Arc`，及时释放 TCB 借用，降低重入和借用冲突风险。

## 五、问答题

### root inode 的作用

root inode 是整个文件系统的根目录，固定编号为 0。它保存根目录的元数据和目录项
数组，目录项把名称映射到 inode 编号；路径解析、文件创建、硬链接、取消链接和
目录列举都以它为起点。因此它相当于文件系统命名空间的入口和锚点。

如果 root inode 的内容损坏，根目录中的名称与 inode 对应关系会失效：文件可能
无法被找到，甚至无法创建新文件；错误目录项还可能指向已释放或无关的 inode。
此时文件数据块不一定立即丢失，但可能因为没有有效目录项而变成不可达空间。
若损坏更严重，位图和 inode 布局也可能不一致，最终需要重新构建文件系统镜像。

## 七、实验反馈

本章难度主要来自文件系统各层的联动：磁盘格式、块缓存、位图、inode 引用计数
以及用户态系统调用必须保持一致。硬链接和普通文件改写本身不复杂，但最后一个链接
删除时的资源回收、间接块释放和缓存同步很容易产生难定位的问题。

建议课程测试增加“超出一个数据块的文件写入后立即读回”“多个硬链接逐一删除后
重新分配 inode”以及“掉电/退出前缓存刷新”的独立检查，使底层错误能够在更小的
测例中暴露。
